# 让语音助手「说话时能被打断」（barge-in）

**触发**：用户说「她再说的时候我不能插话打断吗」「插不进去」「非要等她念完才听我说」；
或反之——打断做了但**把她自己搞哑了/反复被掐**（那是本技能第 0 号坑）。

适用范围：本机麦克风 + 本机喇叭的实时语音回路（Python 侧常驻进程录音 → STT → LLM → TTS 播放），
典型实例是 `~/apex-src/apex-hermes-bridge.py`（:3210）+ `apex_barge.py`，但判据对任何
「边说边听」的回路都成立。APEX 这台机器的实测数字与代码挂点见
`references/apex-barge-in.md`。

## 第一步：先查三处，再下结论（别猜、别急着写代码）

| 查什么 | 命中即说明 | 修法 |
|---|---|---|
| `sd.InputStream` 是否**只在录音函数里**开 | 她说话时麦克风是关的 → 用户插的话**一个字都没录到** | 说话期间常开一支耳朵（独立模块，见下） |
| `/state` 的 `mic_owned` 是否把 `speaking` 也算进去 | 唤醒/拍手监听在**整个说话期间让位** | 说话期间改语义：由「唤醒」变「打断」（注意第 3 号坑：别直接拿拍手当打断键） |
| 播放是不是 `subprocess.run(["afplay", ...])` | 阻塞到整句播完、手里**没有进程柄**，掐不掉 | 换 `Popen` + 30ms 轮询 + `terminate()` |

三层墙都在时，唯一的「打断」就是等她播完（单轮硬顶 180s）——先查清再动手，别靠反复试阈值碰运气。

## 两条腿：掐（输出侧）与听（输入侧）

| 腿 | 要点 |
|---|---|
| **掐** | `Popen(["afplay", ...])` + 30ms 轮询；`_cut_requested()` 一真就 `terminate()`（立刻静音，比「解码后用声卡自己播」省事得多，也不需要 ffmpeg）。加 `POST /interrupt` 供外部掐；`/state` 暴露 `barge{cue,ref,thr,peak,penalty}` 便于自查 |
| **听** | **独立模块**（如 `apex_barge.py`），桥侧 `try/except import`：起不来就 `BARGE_ENABLED=False`，**原有语音链路一行行为都不变**（这是最关键的降级设计）。`arm()/disarm()` 跟着回合生命周期；回合结束**先关耳朵**，把输入设备让给录音函数，别两个流抢设备 |
| **衔接** | 播放循环拿到 "cut" 后**先问判定**再决定「重播当前句」还是「放弃整个回合」；SSE 读循环检测 `aborted` → `break`（关流 = 对端 agent 收到 SIGINT，剩下的字不再烧 token） |

## 判定必须两层证据：快的一层只管「剪不剪」，准的一层才定「算不算」

1. **快（音频域）**：块级 dB 相对「她那一档」抬起 ≥ margin 且持续 ≥ 420ms → cue → 立刻掐。
   目的是**感受上像插话**（400ms 内响应），容许它偶发误判。
2. **准（文本域）**：掐掉之后房间是静的（没有回声干扰）→ 从「他起话头那一帧」起取音频交 STT：
   - 空 / 她自己的回声（成熟实现里已有 `is_tts_echo`，它会拿她的原文做滑窗比对，天生长在这条路上）
     → **假警报：当前句从头重播一次**（不是丢掉半句，也不是让他重说）；
   - 有内容 → 那句**直接当下一轮提问**（一个字不丢，别再开一次麦）。

## 六个坑（全部实测定标，别再踩）

0. **基线没学到就判定 → 她一个字都念不出来**（本次真实事故，用户当场报「发声出错了」）。
   `ref=None` 时门槛落在绝对下限（-44 dBFS），起播第一块就成「持续抬起」→ 实测一轮 **21 次假 cue**，
   她反复被掐断。修：起播头 `REF_LEARN_S=1.2s` **只学不判**，且 `ref is None` 必须走学习分支。
1. **候选插话期间绝不能喂基线**：否则他的第一块声音就把「她的档」顶上去、门槛跟着涨，**永远不触发**
   （自测抓到的真 bug）。只有**短促**抬起（< sustain，多半是她自己的重音）才事后一次性补进基线。
2. **基线别用中位数/分位数**：她自己的语音在她的回放里，**中位数与句子起头重音能差 13 dB**
   （实测 -37.6 vs -24.8 dBFS）。中位数 = 把她的重音当插话；85 分位也压不住峰值。要用**快攻慢放**
   （高了立刻跟、低了 ~1.5 dB/s 放）→ 基线停在「她最响那一档」，再 +margin 才是别人。
3. **判定链里的 STT 也要有有界超时**：第二层「准」的判定要调 STT 才算真插话，而这条请求同样会
   hang（2026-09-12 实测：`api.siliconflow.cn` `Read timed out (read timeout=120)`）。STT 卡住时
   不只是不能插话——**整个对话看起来死了**，用户只能双击结束会话。给 STT 请求 8s + 3 次重试，
   全废就出一句「没听清，再说一遍」，别静默死等；顺带用 `grep -c "stt failed" <bridge 日志>`
   区分偶发抖动（1 次，provider 探针实测正常就别动配置）和系统性故障。
   探针：`scripts/probe-stt-latency.py`（读 config.yaml 的 stt.<provider>，合成 WAV 打三次）；
   完整事故链、日志签名、代码成因见 `references/stt-hang-diagnosis.md`。
   **同一晚的第二刀（同一个文件、同一个用户投诉）**：STT 修完后用户说「识别没之前那么准」——
   不是错觉，也不是模型变差：模型侧换 5 种参数重复跑一字不差，真凶是**语速上限把真人快句当
   「编造」丢了**（`dropped impossible rate: 29 chars / 3008ms = 9.6 chars/s > 8.0`，一天 13 条，
   其中 6-8 条是正常语速的真话）。上限 `8.0 → 11.0`，并把**音频总时长**当分母下界传进守卫
   （页面路径原来压根没传 → 下界从未生效）。回归：`scripts/verify-transcript-guards.py`
   （真人快句 4 例必留 / 编造长句 3 例必杀）。顺带在 `_stt_post` 里打一行模型原始输出
   `[stt] <label> raw(N): ...`——下次「这句识别错了」就能一眼分清是拾音错还是被守卫吞了。
4. **拍手/唤醒检测器不能直接当打断键**：她说话时那支检测器本来就隔几秒出 onset（她自己的声音
   进麦峰值 -18.5 dBFS、flux 500+，而真人拍手 80-235 dB 同一量级）→ 单拍一响就把她掐断。
   要重做必须先量「真人拍手 vs 她回放」的电平差再定阈值。**宁可只留「开口打断」。**
5. **「她的档」被他的插话污染 → 越插越插不进**（2026-09-12 深夜实测定标，用户报「又打不断了」）。
   症状：她的真档 -24.3 dB → 播放期间被顶到 -15.2 → 门槛 -16.7 → 他正常插话峰值 -22.8
   （比真档高 1.5 dB，完全正常的插话）**永远够不到**；每试一次档再涨一次。
   **不是阈值问题**，两处代码成因缺一不可：
   - 桥是**一块一块 TTS** 播的，块间有几秒合成空档；他插话说到一半被块边界/她的句间停顿切开 →
     那 1~12 块的碎片落进 `0 < over < need_blocks` 分支 → 被 `_ref_step(ref, _run_max)` 当成
     「她自己的重音」写进基线 → **他的电平变成了她的档**。`_ref` 跨回合保留，坏值不会自己回来。
   - `set_playing(True)` 每次（**每块**！）`self._over = 0` → 他说到一半的话一到下一块起播就被清零，
     **永远攒不满 13 块 / 416 ms**。
   修：① 候选期一律不喂基线，连 `_run_max` 也不补；② `set_playing` 加块间宽限
   （`APEX_BARGE_GAP_KEEP_S`，默认 2.5s：距上次停播超过这个时间才算她重新开口）；
   ③ `dump()` 暴露 `over / over_ms / run_max_db`，卡在哪一段一眼看出。
   ⚠️ **别试着用「快攻限速」修**：给 `_ref_step` 加快攻上限让基线爬不上去，自测直接挂
   （`assert det._ref == 她的峰值 -24.8` 只到 -35.4）——快攻跟峰值是这套判据的地基。
   完整事故链/数字/补丁位置/已否决修法：`references/baseline-pollution-diagnosis.md`。

## 可行门槛由「回声」决定，不是由算法决定

她回放峰值 -18.5 dBFS 时，门槛就得抬到 -13.5 dB → 等于要用户吼。要「正常说话音量就能插话」，
唯一有效杠杆是**降她的播放音量**（afplay `-v`，用环境变量 `*_TTS_VOLUME` 暴露）：回声低 6 dB，
可行门槛就低 6 dB。所以：

- 所有阈值走**环境变量**（margin / sustain / floor / max / trim / release + TTS 音量），调参不改代码；
- 服务用 launchd 的话，plist 的 `EnvironmentVariables` 段就是调参面板；
- ⚠️ **改 plist 必须 `bootout` + `bootstrap`，`kickstart -k` 不重读 plist**（它用的是缓存的 job 定义）。
  症状：改了 `*_TTS_VOLUME` 重启后音效一点没变，白测一轮。验环境变量真进了进程：
  `ps -Eww -p <pid> | tr ' ' '\n' | grep <前缀>_`。只改**代码**时 `kickstart -k` 足够；
- ⚠️ **还原文件 ≠ 还原进程**：`cp x.py.bak x.py` 之后必须重启那个 job，否则跑着的仍是改过的代码
  （实测有 3 分钟空窗，期间用户还在被误掐）；
- **margin 可以为负**：当「他的电平 ≈ 她的回声」时（实测两边都是 -18.5 dB），把门槛压到**她的峰值之下**
  （实测 -1.5 dB），靠第二级（掐完先转写确认）兜底 —— 误触发的代价只是「当前句重播一次」，
  而门槛高于她的峰值时他就得吼。这是他反复说「还是打断不了」时真正缺的那一步；
- **误判自适应收紧**：判成「不是他」时 margin +2 dB（上限 +8），两分钟无误判松 1 dB；**只对耳朵自己
  触发的 cue 收紧**，外部（拍手/按钮）触发的别拿来调耳朵的阈值；
- **物理限制要先说**：扬声器和麦克风同壳（笔记本）时，「她够响」和「你随便插话」是同一件事的两头——
  两个都要只能**上耳机**（回声消失，门槛可以放到很低）。不先说清，就会出现「调了五轮还是不行」。
- 报数字给用户时用 `/state` 的 `ref_db / thr_db / peak_db` 三个读数（他看得懂，也方便你复盘）。

## 验收：没人插话也能验，但要分清验到了什么

| 手段 | 能证明 | 不能证明 |
|---|---|---|
| 纯函数自测（`python apex_barge.py --selftest`：喂合成电平序列，断言「她的重音不触发 / 他持续 416ms 触发 / 基线没被他的声音顶跑 / 误判惩罚生效」） | 判据逻辑 | 麦克风路径、真实阈值 |
| **注入法**：让她起一轮 → 把一段**不同文本**的 TTS（`edge-tts` 生成）用 `afplay -v N` 从音箱放出来模拟插话 → 对日志 | 整条链：cue → 掐 → 摘录 → STT → 当下一轮提问 | 真人贴麦说话的电平（音箱→麦 vs 人嘴→麦差很远） |
| 真人在场说一句 | 可行门槛是否真够 | ——（这一步必须做，别替用户下结论） |

没人可以插话时直接跑 `scripts/inject-voice-barge-test.sh`（生成注入语音 → `afplay -v 3` → 打印本轮日志）。
**连一个能说话的人都没有时**跑 `scripts/barge-silent-acceptance.sh`：POST `/ask` 让她自己说一句短的 →
只认三条：`/state.barge.cues == 0`、本轮有 `[barge] 回合小结` 且 `cue 0`、没有 `[打断]` / `耳朵起不来`。
这一步只证明「起播不会被她自己判成插话」（坑 0 的回归），**证明不了「他插得进」**——报告里别混为一谈。
**判读只认两行**：① `cue` 之后必有「真插话」或「转写是空的（假警报）」；② 每回合的**小结行
「她的档 X / 麦的峰值 Y / cue N / 门槛 Z」** —— **峰值 Y 就是用户在这轮里到底进了多少 dB**：
Y 一直 ≈ 她的档 = 他插话那一刻的声音**根本没进麦**（时机/朝向），**不是阈值问题，别再调旋钮**。
另外：触发条件 = 连续 13 块（32ms）≈ **416 ms**，单个词可能不够、喊一整句才触发 —— 这条要主动告诉用户。

## 交付纪律（用户对这条特别敏感）

1. **改出声/录音路径前先备份**（`cp x.py x.py.bak-<用途>-<时间戳>`），并记下回退命令。
2. **部署后立刻先跑一轮「静默验收」**：她自己起一轮，`/state` 的 `cues == 0` 且日志
   `[ask] ... spoke n/n lines`（**没有 `[打断]`**）。这一步没做就交付 = 本次的哑巴事故。
3. 再验「他插话」（注入法或真人）。
4. 报告里**把「未验」的项明写出来**（真人音量、距离、噪音未验就说未验）。
5. 中途发现的其他故障**只报告不顺手修**——尤其别在打断还没验完时去改别的链路。
9. **排查阶段也别静默太久**（2026-09-12 两次都被用户当场问「你在干嘛」，第二次已连查 6 个工具
   调用：进程 → `/state` → 日志 → 源码三处）。硬规矩：**调查满 2 条 ssh / 约 4 个工具调用就先发
   一句进展**（哪怕只是「在查，日志已定位到 X，N 分钟内给结论」），再接着深挖。语音链路的
   问题，带时间戳的 bridge 日志通常 **2 条 ssh 内**就能定性（`[listen] utterance` → `stt failed` →
   `conversation ended`），别先把源码全读一遍再开口。先报「证据行 + 时间 + 我的判断」，再继续深挖。
   报告里必须区分**偶发链路抖动**（provider 探针实测正常）和**代码/配置写错**——
   差一个字用户就以为整套语音配置坏了。
10. **不顺手加没被要求的功能**：提议「任何时候拍两下都端窗口」被回「不用了」→ 立刻把本地副本 `scp`
   回线上版本覆盖，**别在工作区留半成品**。
11. **用户问「是不是我的错觉 / 如果没问题就别管它了」时，先给判定 + 数字，别继续往下挖**。
   语音类主观反馈一律三段归因（模型侧排除 → 规则侧统计 → 输入侧物理限制），结论用一句
   「真的，但根因是 X」+ 量化（「今天丢了 13 条，其中 6-8 条是正常人话」）收货；接着**只修
   有证据的那两条**，并把改不动的（远场/无 AEC/快语速）**明写为改不动**。
12. **动一个开关前先说清必要性**：用户会直接问「有必要不？」——一句话给成本/收益
   （正常路径 0.5s 不受影响、最坏从「哑 120 秒」变「24 秒内出声说明」），再动手，别先改后解释。
13. **别在 STT 请求参数上找「识别变差」的原因**：2026-09-12 实测硅基 `Qwen3-ASR-1.7B` 对
   `language` / `prompt` / `initial_prompt` 输出**完全一致**，同一音频重复 3 次一字不差 ——
   杠杆在**音频输入质量**和**守卫会不会把结果丢掉**，不在参数。
7. 用户说「等下」= 立即停手，先报清线上现状（有没有半成品在外面跑）。
8. **一次会话别拉太长**：改代码→部署→联调多轮之后上下文堆满源码 diff 和日志 dump，会越走越慢、
   开始反复重读旧输出（用户会直接说「你开始绕了」）。**在变满之前**把状态落盘成一份交接文件
   （现在跑什么 / 旋钮值 / 只看哪两行日志 / 已否决项 / 遗留待办，例：`~/Desktop/hermes/apex-work/BARGE-STATUS.md`），
   然后**请用户开新会话**（agent 自己不能 `/new`）。

## 相邻的能力缺口：语音轮里「演示某个页面」做不了

用户常要求「让她演示一下财务这一项」。日志签名：
`[ask] '...' -> 0 chars, spoke 0/2 lines (voice)` + `voice turn hit the 180s cap`。
**0 chars** = 整轮没产出，是工具往返撞满硬上限，不是内容问题。根因两条：语音轮**没有任何
「打开/切换页面」的能力**（桥的端点里没有这条路），而系统提示词又只描述了「页面上有什么」、
没定义「演示 = 打开对应页 + 讲要点」。修法方向：给桥加「名称 → URL」映射 + 后台 `open`，
并把「演示 X = 打开 X 的页 + 讲三句要点」写进注入的上下文当约定。
