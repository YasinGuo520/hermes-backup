## 本机语音 UI 的两个量化坑（2026-09-12 实测，Mac APEX 语音链）

适用：本机自研语音界面（Chrome kiosk 页 + Python 桥 + 拍手/唤醒词 + 系统 TTS）。
完整的「根因在权限层」判定与修法在用户侧技能 `mac-local-voice-ui-fix`，此处只记**可量化的部分**。

### 一、朗读在句号处停顿 = 串行合成 + TTS 自带留白

两层原因，**顺序不能反**：

1. **串行合成**：逐句 TTS 若是「合成→播放→合成→播放」单线程，句间要等一次 edge-tts 往返
   （0.5-1.5s）。修：拆成**合成线程 + 播放线程**，合成跑在播放前面（ready 队列）。
2. **每段自带留白**（用 `scripts/measure-tts-gap.py` 量的，zh-CN-XiaoyiNeural）：

| | 前导静音 | 尾部静音 | 三句合计 |
|---|---|---|---|
| 三句分开发（=逐句合成） | 0.185s | **0.87s**（常数，与文本无关） | 9.00s（含静音 3.48s） |
| 同文本一口气发 | 0.185s | 0.86s | 8.18s（含静音 2.66s） |

→ 每个句号接缝 = 上段尾 + 下段头 ≈ **1.05s 死气**，其中 ~0.4s/接缝是逐句合成多出来的。

**修法**：合成线程里用 ffmpeg 把每段首尾削到自然呼吸，输出 WAV 管道（afplay 接受）：

```
silenceremove=start_periods=1:start_duration=0:start_threshold=-45dB:start_silence=0.08,
areverse,
silenceremove=start_periods=1:start_duration=0:start_threshold=-45dB:start_silence=0.26,
areverse
```

→ 接缝静音 **2.10s → 0.65s**（每处 1.05s → 0.32s），总音频 9.00s → 6.82s。
**别削到 0**：留 200-300ms，否则句子黏成一串反而更嗧。

**验收**：给 `synthesised` / `playing` 都打时间戳；若 `synthesised` 一连串在播放开始前就跑完，
后半段即无缝播放，停顿只能来自文本语气本身。

### 二、阈值类参数只能用真事件定（代理信号陷阱）

想验证「拍手检测阈值从 55 抬到 70 会不会漏掉真拍手」时，**合成信号代替不了真掌声**：

| 声源 | flux（该检测器的量纲） |
|---|---|
| 真手拍（历史实测） | **80-235** |
| 人说话 / 自己的 TTS 回放 | **56-90** |
| 键盘点击 / 系统提示音 | **0.9-4.3** |
| 本次**合成**的带通脉冲（当“掌声”用） | **19-39** ← 低一个数量级，阈值 55 和 70 都不触发 |

那次合成实验**什么都没证明**，却极容易被当成「已验证」写进报告。规则：**代理信号必须先与真事件
校准到同一量级，否则它既不能否决也不能确认任何阈值**；定不了就写「此项未验」，把验证压缩成一个
真动作交给用户（如「拍两下手」）。最终 70 是用户真拍确认的。

附一个确实好用的对照技巧：**比较两个参数取值不用改文件重启**——测试脚本里 `importlib` 加载
目标模块，直接覆盖常量（`cw.FLUX_FLOOR = 70.0`）再对同一段输入跑一遍，A/B 立刻出结果。

### 三、误唤醒的声源归因（用户会问「我打字的声音影响吗」）

键盘 0.9-4.3 远低于阈值 → **不是它的锅**；说话声/TTS 回放 56-90 才是。
结构性修法：桥在**整个对话期间**（不只录音/朗读瞬间）上报 `mic_owned`，检测器全程让位；
抬高阈值只是第二道防线。
